# Security and privacy - prototype, not a production sandbox

## What this release constrains

The browser reads only files selected through its file picker. It makes no
external asset requests or default observation connections. Imported text enters
the DOM as text, not HTML. Payload validation bounds size, depth and element count.
The workspace permission helper permits only local record operations; this is a
modeling aid and **not** a security boundary against hostile JavaScript.

The native C observer binds only to IPv4 loopback 127.0.0.1. It rejects unexpected
Host/Origin values, duplicate authority headers, unsupported methods, paths, body
framing and oversized/incomplete requests. Observation requires a 256-bit random
per-launch key generated by the OS. The key is not echoed in snapshot data or
workspace exports. Requests are bounded in time and size. Responses disable
caching and cross-origin framing. No CORS allowances or proxy routes exist.

Only the explicitly supplied HTML and optional regular log are opened. Symlink
final components / reparse points and nonregular files are rejected. This does
not promise that all ancestor directory traversal is symlink-free. Logs are
pre-opened and read, not written. No route changes file paths or executes programs.
The process still has its normal user's permissions: it is not jailed by seccomp,
AppContainer, a VM, capability kernel or a separate restricted OS account.

## What it does not guarantee

C memory safety, compiler correctness, malicious-browser-extension isolation,
local-malware resistance, multiuser machine isolation, constant-time behavior under
all compilers, DoS resistance, end-to-end cryptographic boot attestation and sandbox
escape resistance are not proven. Passing fuzz-like parser cases or sanitizers is
not an independent audit. The single-threaded observer can be delayed by a local
client; timeouts bound one connection but are not comprehensive abuse prevention.

The Windows executable is cross-compiled, unsigned and not runtime-tested here.
It uses a small no-CRT ABI surface with ASLR/NX enabled, but no verified equivalent
of a full modern Windows exploit-mitigation toolchain is claimed. Review/rebuild
before sensitive deployment. Do not disable antivirus or OS protections.
The Linux build enables stack protection, PIE and RELRO; these are mitigations,
not memory safety. Neither executable should run elevated.

## Privacy handling

Workspace exports and local browser storage contain plaintext payloads, notes,
retained history and original imported bytes. They are not encrypted or redacted.
Deleting the browser save does not erase exported backups or current session RAM.
Do not import credentials or private logs unless you intend to store them this way.
No telemetry is sent to us. This release has no analytics, accounts or AI service.

A serial log is untrusted user-supplied data. `reported` does not mean authenticated.
The fixture marker helps avoid accidental confusion, but anyone can edit a log.
SHA256SUMS detects accidental/content changes only when the manifest is trusted;
it is not a signature or identity assertion.

Use the observer only on a trusted local development machine. Do not bind/forward
it onto a LAN, expose it through a tunnel, disable origin checks or publish its URL.
HTML can be served without the key; sensitive snapshots cannot. The URL fragment
is initially present in the console/browser history before the client removes it.
A same-origin script or malicious browser extension could still read in-memory data.

## Future authority gate

Before enabling any host/kernel action: implement hardware-enforced address-space
isolation, capability creation/delegation/revocation, checked IPC, resource quotas,
crash containment and independent negative tests on both architectures. Keep
interpreters and third-party native libraries out of the privileged core. Enforce
permissions at the native boundary, never by trusting a visual button or model.
